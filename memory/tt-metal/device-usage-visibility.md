On bh-glx-110-a10u08 the authoritative "who is using a TT device" source is `/proc/driver/tenstorrent/<N>/pids` (this is what tt-smi reads — `tt_smi/backend.py:386`), or the `processes` array in `tt-smi -s` output. `fuser /dev/tenstorrent/*` and scanning `/proc/*/fd` are NOT sufficient: they silently miss root-owned processes in k8s containers. A root `tt_telemetry_server` (port 18080) normally holds all 32 devices; that is expected and does not block tt-metal runs.

**Caveat discovered 2026-08-26: the pids file goes STALE after a SIGKILL.** A pytest killed hard (background-task kill, `kill -9`) dies without running its device-close path, and `/proc/driver/tenstorrent/<N>/pids` keeps listing the dead PID on every chip it had open — 32 entries for a galaxy run — indefinitely. It reads exactly like "someone else is using all 32 chips". Before believing it, cross-check that the PID is alive: `kill -0 <pid>` (or `ps -p <pid>`), and check for real open FDs with `fuser /dev/tenstorrent/*`. If the PID does not exist AND fuser is empty, the devices are free and the entries are ghosts — do not go hunting for a process to kill, and do not wait for it to clear. The two checks are complementary in opposite directions: the pids file over-reports dead holders, fuser under-reports live root/k8s ones.

**"Free" is not "healthy" (2026-08-27, bh-glx-110-a04u02).** A wedged galaxy shows an EMPTY pids file and still fails every run at mesh open with `RuntimeError: Read 0xffffffff over PCIe ID <n>: the board should be reset`. The health check is enumeration itself: `tt-smi -ls` (or `-s`) crashes with the same message inside `tt::umd::TopologyDiscovery`, so if `tt-smi -ls` cannot print the board table, the galaxy needs a reset regardless of what the pids file says. Fix: **`tt-smi -glx_reset`** (`-glx_reset_auto` is the same with up to 3 retries; `-glx_reset_tray {1..4}` for one tray). ~90 s, issues USER_RESET on all 32 devices, then IPMI reset, then POST_RESET and re-init. Plain `-r` is per-PCIe-device and is NOT the galaxy path. No sudo needed — the sudo allowlist here is SLURM tooling (`tt_reidle_downed_node.sh` sets a SLURM node state, it is not a board reset) plus one raw `ipmitool` command that `tt-smi` already wraps. Run `tt-smi -ls` afterwards to confirm all 32 Blackhole rows come back.

**Two more states worth separating (2026-08-27, a04u02).**

1. *Enumerating but every run hangs.* `tt-smi -ls` lists all 32, compute runs, kernels compile, then the FIRST fabric collective a run reaches never completes (host spins on the completion poll). This turned out NOT to be hardware: it was **uncommitted submodule pointer drift** (a `umd` rename + a new Galaxy cluster descriptor, dated 2026-08-26) in the shared NFS checkout, plus the build on top of it. Reverting both pins and rebuilding fixed it. Because `/data` is NFS the bad build hit every box at once, which is exactly why it read as a hardware story. **On a shared checkout, check `git status` for same-day submodule drift BEFORE theorising about the fabric.** See `~/debug-docs/mistral4_prefill_planning-noissue/part2/MISTRAL4_HANG_ROOTCAUSE_submodule_drift.md`.

2. *MMIO-unresponsive between runs (real, and still present).* Mesh open dies with `RuntimeError: MMIO per-op timeout: 4B load took N us (budget=2 ms)` or `Read 0xffffffff over PCIe ID <n>` at `ttnn/ttnn/distributed/distributed.py:631`. One `tt-smi -glx_reset` clears it. **It can enumerate cleanly two minutes before failing**, so `tt-smi -ls` passing does not predict that the next mesh open will succeed — just reset and retry.

So the health ladder is: pids file (who holds) -> `tt-smi -ls` (PCIe) -> a run actually completing (build + fabric). Neither of the first two is health.

**On bh-glx-120-b03u02 `/proc` is mounted `hidepid=invisible`, which breaks every owner-attribution check (2026-09-15).** `ps -eo user --no-headers | sort -u` returns your own username and nothing else, so anything that tries to identify a *holder* is blind to other users and fails silently in the safe-looking direction. Four such checks, three of them mine:

1. `fuser /dev/tenstorrent/*` — sees only your own processes; prints empty while someone else holds all 32.
2. Filtering the pids file by `stat -c %U /proc/<pid>` — another user's `/proc/<pid>` does not exist, so the holder is dropped. **This produced a false "chips free" in a handoff while a colleague had a live 4-rank run on all 32.**
3. `[ -s /proc/driver/tenstorrent/N/pids ]` — procfs reports `st_size=0` while the content is populated, so the test is always false. Use `p=$(cat ...); [ -n "$p" ]`.
4. `kill -0 <pid>` / `ps -p <pid>` to test whether a listed holder is alive — the advice above. Under `hidepid` another user's live PID gives EPERM, not ESRCH, so "cannot signal it" does not mean "it is dead".

**`~/scripts/tt-devs.sh` supersedes all of the above, and it is right where the pids file is wrong (2026-09-19).** It reads the UMD `CHIP_IN_USE` robust mutex in `/dev/shm` (world-readable, cross-user, carries `owner_pid`) plus `tt_aiclk` from sysfs (no `/proc` at all, so `hidepid` cannot blind it), and names hidden holders via cgroup v2. **Trust it over the driver pids file.** Concrete case: every chip's `/proc/driver/tenstorrent/<N>/pids` listed PID 630435, `kill -0` returned EPERM (which the note above says means "alive, another user"), and the chips were in fact completely free — the entries were ghosts of a dead process and EPERM was ambiguous, not decisive. `tt-devs.sh` correctly reported all 32 free and a full 8-rank galaxy job started immediately. Its own blind spots are documented in its header; the one that matters is a containerized job with a private `/dev/shm`, which no host-side signal besides `aiclk` can see.

**What works:** read the PID *numbers* out of `/proc/driver/tenstorrent/<N>/pids` and do **not** try to attribute them — treat any PID you cannot see as someone else's. Then read the *pattern*: **one PID listed on all 32 chips = the root `tt_telemetry_collector`, i.e. idle** (confirm with `curl -s -o /dev/null -w '%{http_code}' localhost:18080` → 200). **Four distinct PIDs at 8 chips each = a live 4-rank galaxy run.** Also check `ls -l /dev/shm | grep -v " $(id -un) "` for another user's `tt_prefill_*` or `TT_UMD_LOCK.CHIP_IN_USE_*`.

**And `run_matrix.sh`'s reset guard is dead code on such a box.** `OTHER=$(ps -eo user,pcpu,cmd | awk -v u="$USER" '$1!=u && $2>50' | grep -icE "pytest|python")` can never match under `hidepid`, so `OTHER` is always 0 and the "NOT resetting: another user's job is live" branch is unreachable — it will `tt-smi -glx_reset` on **every** cell failure, unconditionally, and can reset out from under a colleague's live run. There is no guard, only the appearance of one. See [[glx-hard-kill-needs-reset]].

Nothing in the monitoring stack attributes device usage to a user. The k8s `tt-metrics-exporter` (:9105, tenstorrent/tt-metrics repo, PRIVATE) reads sysfs only and exports `tenstorrent_{temp_celsius,power_watts,voltage_volts,current_amps,ai_clk_mhz,pcie_*}` labelled by `node` — no user/job/pid/utilization label, and the shipped Grafana dashboard has no such panel. Activity is only visible indirectly as power/temperature/PCIe-traffic movement.

As of 2026-08-23 kmabee's SLURM job (partition `bh_sc36_6`, `Command=/usr/bin/bash`) is a placeholder holding the node with `AllocTRES=cpu=1,node=1` — no gres for the devices — while the real pytest work runs in an ssh/tmux cgroup (`/user.slice/...session-N.scope`), not under `slurmstepd`. So SLURM accounting shows an idle 1-CPU allocation no matter how busy the 32 chips are. Expect colleagues to say "I don't see you using the devices"; point them at the driver pids file instead.
